### Proposal editing handoff

`POST /api/recommendations/revise` accepts `RecommendationRevisionRequest` from
`@wizard-ads/shared/recommendation-revisions`: `requestId`, `profileId`, `recommendationId`,
`expectedRevisionId` (null for the original proposal), decimal-string `proposedValue` and a
required `note`. The server derives the actor; owner/admin/analyst review permissions apply.
Same-origin JSON and a bounded body are required. Retry the same normalized request after a
lost response; its immutable receipt is historical, so refresh the row before further review.

`listRecommendationWindow` now returns the effective proposal value and `proposalRevisionId`.
Editing resets prior acceptance/dismissal to `proposed`. Both existing decide/export endpoints
accept `expectedRevisions: [{ recommendationId, revisionId }]` covering every explicitly selected
ID. Edited proposals require those references. Missing/stale decision rows remain counted in
`refused`; `unavailable` does not reveal whether another tenant owns an ID. An explicit export
refuses the whole selection if any row is missing, nonaccepted or stale. Export freezes the
revision, and the native preview verifies that identity and exact monetary values again.

Claude's client components are unchanged. Use
`apps/web/src/recommendations/revisions-http.test.ts` and
`packages/db/src/queries/recommendation-revisions.test.ts` as synthetic lifecycle fixtures.
The 28 affected web tests passed, including actual JSON and Excel downloads; DB review and
custody checks, shared tests and typechecks are recorded in the audit. No Amazon approval is
created merely by editing, accepting or exporting a proposal.

### UI integration contract

Use the schemas in
[`packages/shared/src/sp-write-application.ts`](../../packages/shared/src/sp-write-application.ts)
as the authority. Existing session authentication, assurance checks and owner/admin
capability apply; the server supplies the actor. POSTs require same-origin JSON.

| Endpoint | Request | Result |
|---|---|---|
| `POST /api/sp-writes/preview` | `SpWritePreviewRequest`: `requestId`, `profileId`, `applyBatchId` | `SpWritePreview`: exact plan, binding and frozen source evidence |
| `POST /api/sp-writes/approve` | `SpWriteManualApprovalRequest`: `profileId` and the shared manual approval object | `SpWriteAdmission`: operation identity and `queued` or `approved_pending_start` |
| `GET /api/sp-writes/status` | `profileId`, `executionId`, `planId` | `SpWriteOperationDetail`: receipt, execution accounting, mirror counts and original/inverse links |
| `POST /api/sp-writes/inverse-preview` | `SpWriteInversePreviewRequest`: `requestId`, `profileId`, `original: { executionId, planId }` | A new exact inverse preview; submit its separate confirmation through the same approval endpoint |

Present the exact profile, entities, old/new values, guardrails and count before the
Amazon-named confirmation. Retain the original approval request identity and payload on
retries; a lost response must not create another confirmation. `approved_pending_start`
means approval exists but enqueue is not yet confirmed. Preserve both operation IDs:
the original and inverse may share an execution cycle but have different plans.

Amazon acceptance, subsequent observation and local mirror reconciliation are distinct
states. In particular, provider success can coexist with `mirror.pending > 0`; the screen
must not claim local synchronization has completed in that state. Only a fully observed
forward plan whose current values still agree can produce the guarded full-plan inverse.

### F1. Current main cannot run against the reported 41-version queue schema

The hosted queue schema stops at migration `20260901010000` with 41 versions. Five merged
migrations, `20260901020000` through `20260901060000`, are not applied. Since commit `ed7cb78`
(WP-194, 2026-09-02) the shared row parser `packages/db/src/queries/job-wire.ts:51-62` reads
`row.claim_token` from every claimed job; the hosted `claim_sync_jobs` returns
`setof public.sync_jobs` without that column, so the parser throws
`claim function returned an invalid claim capability` after the claim UPDATE has committed.
`apps/worker/src/store.ts:307` and `:342` also reference `claim_token is null` in SQL, which
raises `column does not exist`. The Vercel cron route
`apps/web/app/api/cron/sync/route.ts:97-101` builds `PostgresWorkerStore` and `SyncWorker` from
`@wizard-ads/worker` on main, so a web deploy from main hits the same throw on every tick, leaves
claimed rows `running`, and burns attempts to dead through `requeue_stale_sync_jobs`.

Consequence: revisions containing WP-194 must not claim jobs against that schema. The actual
parser was exercised with an absent column and with SQL null: the former throws and the latter
returns `claim: null`. The database commit/recovery behavior still needs the disposable upgrade
rehearsal in WP-207. Other components must be checked by their schema dependencies, not by date.
